# 定义：把共同问题做扎实

> 状态：骨架。本章的单元契约见 [PLAN.md](../PLAN.md)，症状入口见 [手册目录](./README.md)。

## 这一章解决什么

工作一开始最常见的失败不是代码写错，而是共同问题没有形成：目标含糊、边界漂移、事实与猜测混在一起、验收条件缺失。这一章把"手头的变更"推进成一个可执行、可验收的共同问题。

## 单元

### 1.1 从手头变更到共同问题

- **情境**：有人提了一个请求，团队对"要解决什么"只有各自的理解。
- **动作**：把变更写成一张卡：目标使用者与时刻、要改变的行为、非目标、硬约束、owner、当前未知项。
- **带走**：变更工作卡。
- **门**：每个非目标都写出来了；至少一个未知项被显式标注；owner 是具名人。

### 1.2 把事实、假设、意见与未知项分开

- **情境**：讨论里事实、猜测和个人偏好混在一起，无法判断哪句话可以依赖。
- **动作**：把材料按来源、摘录、日期、适用范围、状态和事实 owner 登记；未知项单独成列。
- **带走**：事实底稿与待确认问题清单。
- **门**：每条事实有来源和适用范围；没有来源的陈述被标为假设或意见。

### 1.3 拿不定主意时，先获得会改变决定的证据

- **情境**：两个方向都可行，团队在争论而不是在获取信息。
- **动作**：写一张决策证据卡：答案 A 时做什么、答案 B 时做什么、最小证据动作、停止条件、谁回写。
- **带走**：决策证据卡与结论。
- **门**：两种答案导致不同动作；证据动作有明确停止条件；结论被写回权威产物。

### 1.4 把已经足够清楚的意图固定成可执行规格

- **情境**：意图已经稳定，但下游仍要反复问"到底要什么"。
- **动作**：写 spec：用户视角的目标、可观察行为、边界与非目标、验收证据、未决项。
- **带走**：一份可被实现和验证消费的 spec。
- **门**：每条行为有验收方式；未决项没有被写成承诺；不写容易过期的文件路径。

## 章末质量门

- 一个没有参与讨论的人，能否只读这些产物就说出要做什么、不做什么、怎样算完成？
- 每个未知项是否有 owner 和下一次确认的时间点？
- 是否把"意见"误写成了"事实"？
