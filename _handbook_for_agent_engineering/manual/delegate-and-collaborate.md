# 委派与协作：让执行者独立，让责任可见

> 状态：骨架。本章的单元契约见 [PLAN.md](../PLAN.md)，症状入口见 [手册目录](./README.md)。

## 这一章解决什么

委派失败通常不是执行者能力不够，而是 brief 不完整、可写范围不清、验证方式没给、责任没有落到人。协作失败通常是"并行"掩盖了共享状态或未决决定。这一章把"交出去"变成一份可独立执行的上下文，把"一起做"变成一组可追溯的责任。

## 单元

### 3.1 为一个工作包准备最小上下文

- **情境**：执行者（人、agent 或子代理）拿到任务后仍要反复问，或者猜错方向。
- **动作**：写任务上下文包：目标、权威产物指针、可写范围、禁止动作、验证命令、权限与人工确认点、报告形状。
- **带走**：一份可独立执行的 brief。
- **门**：执行者不需要看上一段聊天；每个"不能做"都有明确边界；验证方式是可运行的。

### 3.2 为同一项变更安排人、agent 与会话

- **情境**：多个角色或多个 agent 同时参与，谁决定、谁审核、谁合并不清楚。
- **动作**：写协作约定：artifact owner、决定 owner、执行者、集成 owner、可写范围、权限、人工 gate、升级路线。
- **带走**：协作约定。
- **门**：每个共享产物恰有一个 owner；升级路线能回答"卡住了找谁"。

### 3.3 让并行工作重新汇合并可交接

- **情境**：几条工作线各自完成，但合在一起行为不一致，或没人知道当前状态。
- **动作**：准备汇合与交接包：共同来源、已接受输入、每项实际引用、兑现行为、验证证据、冲突处理、残余风险、下一位入口。
- **带走**：汇合与交接包。
- **门**：不复制 spec、决定或 diff 作为第二套真相；冲突有明确的回流 owner；下一位能从这里开始。

## 章末质量门

- 如果主执行者明天消失，下一位能否只读产物继续？
- 有没有"并行但共享同一文件/分支/key"的工作线？
- 语义冲突（不是文本冲突）由谁裁决？
