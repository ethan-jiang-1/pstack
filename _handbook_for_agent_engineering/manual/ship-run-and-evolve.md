# 交付、运行与演进：让变更安全地进入真实环境

> 状态：骨架。本章的单元契约见 [PLAN.md](../PLAN.md)，症状入口见 [手册目录](./README.md)。

## 这一章解决什么

合入不等于交付，部署不等于允许用户触发，CI 绿不等于可以发布。这一章把"进入真实环境"拆成一个可复核的风险结论、一个从运行信号开始的下一轮，以及一组按顺序落地的变更。

## 单元

### 5.1 在交付前给出可接受的风险结论

- **情境**：版本要上线，团队只有"应该没问题"和一堆 CI 绿。
- **动作**：对固定版本、部署目标和暴露范围写交付风险结论：承诺证据、评审、未关闭回流、运行前提、具体风险、暴露限制、观察信号、停止/回退/补救、owner、风险接受人、重新打开条件。
- **带走**：交付风险结论。
- **门**：结论只能是现在交付、限制暴露、等待补证据或不交付；不能由自动化评分替代具名人。

### 5.2 从运行信号开启下一轮变更

- **情境**：线上出现指标、trace、审计事件、用户反馈或依赖变化，团队直接开修。
- **动作**：先把信号放回固定交付上下文：版本、配置、暴露范围、时间、基线、原始样本、已观察事实、已确认影响、止损、未知与原因假设；再选择下一步。
- **带走**：运行信号记录与再进入工作卡。
- **门**：事实与原因假设分开；止损先于根因；下一步有明确入口。

### 5.3 按顺序落地一组变更

- **情境**：一串 PR 都已绿，但落地顺序、独立验证和停止点不清楚。
- **动作**：为每个 PR 取得非作者的独立 verdict；从最低未合并 PR 开始，只落地连续通过的一段；用 patch-id 检查旧 verdict 是否仍覆盖当前 head；一次合一个，落地过程中不动栈。
- **带走**：栈、每 PR 的 verdict、连续落地段与停止点。
- **门**：绿 CI 和 bot approval 不算 verdict；作者自证不算独立验证；第一个没有 verdict 的 PR 就是停止点。

## 章末质量门

- 这次交付的暴露范围是否小于"所有人"？如果不是，为什么？
- 如果明天必须回退，回退动作和负责人是否已经写明？
- 落地序列里有没有"看起来通过、其实 verdict 覆盖的是旧 SHA"的 PR？
