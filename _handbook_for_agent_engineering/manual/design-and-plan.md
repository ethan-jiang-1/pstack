# 设计与计划：让工作可兑现、可委派

> 状态：骨架。本章的单元契约见 [PLAN.md](../PLAN.md)，症状入口见 [手册目录](./README.md)。

## 这一章解决什么

定义回答了"要什么"，这一章回答"怎样把它变成可以独立完成、可以验证、可以交接的工作"。核心不是画架构图，而是把承诺变成行为、把行为放进可测试的形状、把形状切成有阻塞边的工作包。

## 单元

### 2.1 先把承诺变成可观察的行为

- **情境**：spec 里是抽象承诺，实现和测试各自解释。
- **动作**：为每条重要承诺写一张行为卡：观察位置、成功信号、失败出口、人工接手点、非目标。
- **带走**：行为地图。
- **门**：每条行为都能被至少一个独立判据观察；失败出口不是"报错"三个字。

### 2.2 设计可实现、可测试的模块形状

- **情境**：代码能写，但测试必须越过接口看内部状态，或者改动总是牵连多处。
- **动作**：定接口、不变量、切口和测试表面；先画 `not implemented` 的形状，再填实现。
- **带走**：模块形状卡。
- **门**：测试只通过公共切口；接口能表达调用者需要知道的全部事实；没有为了测试而暴露内部状态。

### 2.3 拆成可以推进、可以交接的小工作

- **情境**：工作太大，一个人或一个 agent 无法在一个上下文里完成。
- **动作**：切成端到端的工作包，声明阻塞边、可写范围、验收条件、完成检查。
- **带走**：工作包列表与依赖图。
- **门**：每个包本身可演示或可验证；阻塞边没有环；每个包有明确的 owner 或领取条件。

## 章末质量门

- 任取一个工作包，一个陌生人能否只读它就开始，不需要问上一段聊天？
- 有没有"看起来并行、实际共用同一份可变状态"的包？
- 每个包完成后，能否用它自己的检查证明，而不是靠整条链的测试？
