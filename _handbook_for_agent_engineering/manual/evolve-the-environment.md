# 让环境变好：把摩擦变成下一轮的优势

> 状态：骨架。本章的单元契约见 [PLAN.md](../PLAN.md)，症状入口见 [手册目录](./README.md)。

## 这一章解决什么

同一个纠正反复出现，说明当前的做法缺一条结构性约束；spec 和决定越积越多、方向开始漂移，说明缺少退役与阶段边界。这一章把"下次注意"换成仓库里的检查，把"历史包袱"换成有状态的记录。

## 单元

### 6.1 把反复摩擦变成有证据的改进

- **情境**：评审、失败回流、运行信号或交接里反复出现同一类成本。
- **动作**：建摩擦证据账本：把独立记录按共同工作条件关联，保留实际摩擦、成本、临时绕过、共同与不同条件、尚未证实的解释、下一步；再写改进提案：共同机制、成本、主要杠杆、范围、非目标、最小第一步、owner、保护性验证、停止条件。
- **带走**：摩擦证据账本与改进提案。
- **门**：不是按情绪排序的技术债清单；每条改进有证据和成功信号。

### 6.2 把教训编码成结构

- **情境**：同一条指令已经写过第二次，或者 operator 反复纠正同一类错误。
- **动作**：按可靠性排序找约束：架构 → 类型 → 错误信息本身就在说怎么修的 lint → 测试 → 文档。每条新检查都要在一个真实历史错误上证明它会失败。
- **带走**：一条会失败的检查或类型约束。
- **门**：检查在历史错误上真的会红；不是只加了一段"请注意"。

### 6.3 多轮之后收回累积的承诺与上下文

- **情境**：多轮迭代后，已经发布的 spec、决定和交接件不再代表当前方向，但下一位仍把它们当权威输入。
- **动作**：列累积清单，标注每份的状态；对不再算数的承诺写退役记录（被什么取代、由谁宣布、从何时起失效、从哪里摘下入口）；为下一次上下文切换写阶段边界计划。
- **带走**：退役记录与上下文计划。
- **门**：读者能从当前入口分辨哪份还算数；退役不是删除历史，也不是就地改写成新 spec。

## 章末质量门

- 这次改进如果下个月被遗忘，仓库里还有什么会拦住同类错误？
- 有没有一份已经很危险的 spec 仍然挂在入口上？
- 下一次换会话/换 agent 时，哪些上下文应当继续、清空、交接或压缩？
