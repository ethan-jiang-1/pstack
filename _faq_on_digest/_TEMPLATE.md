# 新 FAQ 模板

新问题按编号建立目录，例如 `07_short-descriptive-slug/`。编号保留提问历史，slug 描述读者面对的实际问题。

## 必需文件

`question.md` 记录问题的范围和前提：

```markdown
# <读者实际会问的问题？>

> [FAQ 首页](../README.md) · [直接回答](./answer.md)

## 问题要解决什么

<用一两段说明场景、前提和不在本问题范围内的事情。>
```

`answer.md` 先让读者能行动，再提供理由：

```markdown
# <同一个问题，用可扫描的表述>

> [FAQ 首页](../README.md) · [问题原文](./question.md) · [相关系统说明](../../_digest/<path>.md)

## 直接回答

<一句结论。>

## <中间小节：标题按问题自拟>

<决策条件、步骤和例外。>

## <需要时再加一节，同样自拟标题>

<只保留理解结论所需的机制；深入解释链接到 _digest。>

## 继续阅读

- [当前行为的源码](../../skills/<name>/SKILL.md)
- [相关系统说明](../../_digest/<path>.md)
```

只有 `## 直接回答` 和 `## 继续阅读` 是固定标题。中间几节按问题起解释性标题，不要照抄占位标题。

## 可选补充页

只有在一个维度会让主回答明显变长时才新增，例如 `dependencies.md`、`examples.md` 或 `harness-notes.md`。补充页必须：

- 用完整标题说明它解决什么，不要叫"补充"；
- 链回 `answer.md` 和 FAQ 首页；
- 区分当前事实、可变的实现细节和历史背景；
- 不重复主回答已经给出的结论。

## 提交前检查

1. 结论是否和根目录 `README.md`、相关 `SKILL.md` 一致？
2. 是否把某个 harness 的行为误写成所有 harness 的通用行为？
3. 是否把模型 slug、默认预算、skill 数量写成不带基线的永恒事实？
4. 本地链接是否都能解析，首页是否能找到新问题？
5. 相邻 FAQ 是否会给读者相反的建议？
