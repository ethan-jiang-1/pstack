# `unslop`

> 源码：[`skills/unslop/SKILL.md`](../../skills/unslop/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

把 AI 文本的表面习惯拆成一张按类别编号的清单，逐类扫描后直接重写。规则编号是稳定 id，供其他 skill 引用，所以它更像一份可点名的词表，而不是一份需要逐条背诵的规范。

## 它解决什么

AI 写的英文通常没有语法错误，问题是一组高频习惯叠加出来的味道：内容上编造来源，语言上膨胀，格式上过度装饰，语气上残留聊天机器人腔，再加上填充、对冲、术语堆砌，以及"描述感觉而不描述机制"。

这些毛病单看都很小，删掉任何一条也不会让文章变好多少。合在一起，读者会在第一段就感到"这是生成的"。`unslop` 的做法是先给味道命名，按类别分组，然后整段重写。它保留原意，也要求匹配原文语气，所以不是把所有文字压成同一种干瘪风格。

## 核心机制

### 1. 七类分组

现存规则分在 Content、Language、Style、Communication artifacts、Filler、Jargon、Plain speech 七组。分组是目录，不是扫描流水线：源码只说 "scan for the patterns below, then rewrite"，没有规定顺序，也没有把标点与格式放在最后（Style 是第三组）。

### 2. 编号是接口

规则编号是稳定 id。删掉一条规则要留下空号，不能重排。因此现存编号里缺 1、2、4、6、21，顶到 33。这个约定服务的是引用：`poteto-mode` 的正文引用 "unslop rule 14"（句中冒号），`technical-writing` 把新增的隐喻词作为 rule 26 的补充提案。规则表因此成了一个共享命名空间，其他 skill 是提议者，`unslop` 是词表的 owner。

### 3. 三条接近绝对的规则

- **rule 13，em dash。** 标题写 overuse，正文要求完全避免，连括号、短横替代和 en dash 都不接受。需要停顿就断句或用逗号。
- **rule 14，冒号。** 只在列表或例子前可用，不能当句子中段的连接件。用冒号引出对照，往往是在替一个站不住的句子搭脚手架。
- **rule 26，抽象隐喻名词。** 一张点名表，包含 substrate、wedge、vector、locus、harness、surface、ratchet、evacuate、endgame、north star 这类词。要求换成具体词，或者用机制的真名。这是整份清单里最长之一、也最容易过时的一条。

这三条之所以接近绝对，是因为它们是最可靠的生成痕迹，逐例权衡的成本高于一律禁掉。

### 4. 成对的压力

rule 23、28、30 要求删填充、拆长句、去副词；rule 33 反过来禁止 over-compression：不丢冠词、不写无动词片段、不用符号和缩写让读者解码。两条方向相反，合起来定义的是"短而不碎"，而不是越短越好。

### 5. 唯一的内容级测试

rule 27 要求说机制而不是感觉，并给出一个可执行的检查：如果一句话可以原封不动出现在另一个项目的文档里，它就没有说这个项目的任何事。这是整张表里最硬的判据，因为它不依赖"读起来像不像 AI"，而依赖信息量。

### 6. 输出是改过的文本

流程只有两步：扫模式，重写。交付物不是问题清单，也不是评分，是改完的文字。这也意味着它适合作为一个 pass 插在写作和发布之间。

## 设计意图

- **先命名，才能检测。** 没有名字的味道只能靠直觉争论；有编号之后，评审可以说"这是 rule 16"。
- **分类让评审能按组定位。** 七组是目录，不是扫描顺序；源码没有要求从内容到格式逐层过一遍。
- **稳定 id 换引用稳定。** 空号是阅读成本，换来的是别的 skill 可以长期指向同一条规则。
- **绝对规则替代逐例判断。** em dash 在生成文本里出现得太频繁，一律禁掉；冒号只禁句中连接，列表和例子前可以用。
- **反向规则防过度矫正。** 清理的目标是清楚，不是把文章削成电报。
- **可移植性测试把"具体"变成判断。** 不要求作者更有文采，只要求写出这个项目独有的东西。

## 依赖关系

- **独立。** 仓库 README 把它列在"不调用其他 pstack skill、可单独安装"的一组，任何英文写作表面都能直接用。
- **下游很广。** `poteto-mode` 规定所有散文表面（包括给用户的回复）走 `unslop`；`teach`、`recall`、`blast-radius`、`show-me-your-work`、`automate-me` 与 benny 的自动化都点名它；`opening-a-pr` 对 PR 描述与 commit body 应用它。
- **与 `technical-writing` 的分工。** `technical-writing` 把 slop 目录整体委托给 `unslop`，自己负责文档模式（Diátaxis）与句法层（Google developer style、STE、Global English）。两者叠加使用，不互相替代。
- **提案关系。** `technical-writing` 要求把新发现的隐喻词和替换词作为 rule 26 的补充提案写进回复，附 diff，并且明确不要直接编辑 `unslop`。词表变更因此走提案，不走就地修改。

## 使用边界

- **不做事实核查。** rule 5 要求含糊归因要么点名来源要么删除，但它没有能力验证来源是否真实。它清的是措辞，不是真伪。
- **不负责结构。** 一篇把 tutorial 写成 reference 的文档，逐句都合格也仍然错；那是 `technical-writing` 的 Diátaxis 层。
- **规则是英文绑定。** AI 词表、title case、弯引号、冠词都是英语现象。用在中文或其他语言上只能迁移精神（具体、主动、完整句），不能逐条套用。
- **绝对规则有真实成本。** 合理使用 em dash 也会被禁；冒号在列表和例子前仍可用。这是有意的取舍，不是疏漏。
- **词表会过时。** 它记录的是某个时期的模型习惯，换一代模型会换一批 tell。更新时只能新增编号，不能重排。

## 值得注意

- **缺号是阅读成本。** 第一次读的人会以为 1、2、4、6、21 被漏掉了，实际是已删除规则留下的位置。
- **规则没有严重度。** 28 条现存规则平铺，一次机械 pass 完全可能修掉所有格式问题，却漏掉 rule 27 这种最需要判断的一条。
- **没有回读验证。** 技能要求保留原意，但重写之后是否真的保住了，只能靠人再读一遍。长文上这是实打实的风险。
- **rule 13 的标题与正文强度不一致。** 标题写 overuse，正文要求完全避免；只读标题的引用者会低估这条规则的硬度。
- **与 `technical-writing` 的禁则部分重叠。** em dash 两边都禁；分号与斜杠是 `technical-writing` 的规则，`unslop` 没有对应条目。两处维护，存在慢慢不一致的风险。

## 关键洞察

1. **slop 是一组可命名的表面习惯，不是能力问题。** 命名之后才能逐条清除。
2. **编号是接口。** 稳定 id 让规则可以被别的 skill 引用，空号是为兼容性付的价。
3. **绝对规则比逐例判断便宜。** 对最可靠的生成痕迹，一律禁掉省下的争论多于损失。
4. **清理需要反向规则。** 没有 rule 33，去 slop 会把文章推向另一种机器腔：电报体。
5. **唯一实质的测试是信息量。** 一句话放到别的项目也成立，它就等于什么都没说。
