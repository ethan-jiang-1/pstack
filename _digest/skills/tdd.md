# `tdd`

> 源码：[`skills/tdd/SKILL.md`](../../skills/tdd/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

修一个有便宜测试路径的 bug 时，先把坏行为变成一条会失败的测试，再改生产代码。真正的交付物不是那次修复，而是"修改前失败、修改后通过"这对可复核的证据。

## 它解决什么

bug fix 最常见的证据缺口是"修好了"这句话本身：它无法区分"改掉了触发条件"和"改掉了症状"，也无法在三个月后证明这个行为曾被锁住。回归测试把这句话变成一条可执行的断言，而且在 git 历史里，失败的那次提交可以先于修复落地。

但强制 TDD 的代价同样真实：需要搭整套 harness、写脆弱的 mock、跑慢的端到端环境、依赖只在生产存在的状态，或者复现步骤本身就说不清。`tdd` 因此不是一个"必须测试"的命令，而是一道带明确失败出口的判定：能便宜地测试就先红后绿，不能就用最接近的可执行检查，并且说明为什么。

## 核心机制

### 1. 入口是一道判定

frontmatter 的 description 同时写了触发和跳过：用户显式要求 TDD、失败测试或回归测试，或者这个 bug 有一个显而易见的便宜本地测试目标时才用；测试路径不清楚、昂贵、集成很重、或没被要求时跳过。这是 pstack 的 skill description 里唯一显式写 `Skip when...` 的一份。

### 2. 六步里只有第 4 步是硬的

流程是：理解 bug、选最窄的可执行检查、先写失败测试、修之前运行它、做最小修复、再跑一次。其中"修之前运行，确认它因为预期原因失败"是整个技能承重的一步。一条没被观察过失败的测试，不知道它锁住的是 bug 还是别的东西。

### 3. 最窄的可执行检查

优先复用该代码路径上已有的单元、组件、集成或回归测试，而不是为流程从零搭一套。源码明确写了不要为了满足工作流而新建 harness。这条规则让测试成本与该代码原有的验证方式对齐。

### 4. 测试写应然，不写实然

测试要编码期望行为，而不是镜像当前实现。写成镜像的测试会在下一次重构时误报，于是 team 学会忽略它，回归保护随之消失。

### 5. 不可测时的替代清单

跳过一个新测试不等于放弃验证。源码给出的替代是可执行检查：定向脚本、手工复现命令、浏览器自动化、快照对比、日志断言、聚焦的集成检查。判断标准是"宁可不加测试，也不加坏测试"，并给了坏测试的五个特征：主要在测 mock、编码当前实现细节、依赖时序或无关全局状态、为小修需要昂贵基础设施、证明完就该删掉。

### 6. 报告的是证据形状

最后一步固定三项：失败在前的那条测试或检查及其失败输出；通过之后的运行与附近的验证；如果无法展示失败在前，说明原因和实际用的替代检查。这把"我测过了"拆成可被 reviewer 复核的三件事。

## 设计意图

- **失败优先是唯一便宜的防假阳性手段。** 先看到红，才知道绿有意义。
- **把"要不要测试"从意志问题变成条件问题。** 不可行清单让跳过也成为合规结果，避免仪式化的测试。
- **测试是回归契约，不是实现快照。** 写应然才能让它在重构后继续有效。
- **最小生产改动。** 在满足期望行为的同时保住邻近契约，防止顺手重构扩大 diff。
- **证据格式固定，评审可核。** 报告结构由技能规定，而不是由 agent 自由发挥。

## 依赖关系

- **独立。** 仓库 README 把 `tdd` 列在"不调用其他 pstack skill、可以单独安装"的一组里。
- **上游调用。** `poteto-mode` 的 [bug-fix playbook](../../skills/poteto-mode/playbooks/bug-fix.md) 第 5 步引用它来决定先失败后修复的提交顺序；`poteto-help` 的 recipes 与 `automations/benny` 的 issue 修复流程也点名它。这些调用只引用节奏，不复制规则。
- **与 bug-fix 的分工。** playbook 负责在真实表面复现并取得运行时证据，`tdd` 负责把其中便宜的部分固化成测试。playbook 还写明：单元测试显示分支行为，不证明 bug 不存在。所以两者不能互相替代。
- **原则归属。** bug-fix playbook 称这一步是 `sequence-verifiable-units` 的典型；`tdd` 自己的正文没有点名任何 principle，引用关系在 playbook 一侧。
- **相邻能力。** 测试路径昂贵时，`create-verification-skill` 生成的 `verify-*` skill 或项目已有的 control skill 才是取证手段。

## 使用边界

- **不是通用 TDD。** 正文标题是 "TDD Bug Fix"，只讲修 bug，没有 refactor 阶段，也不覆盖"新功能先写测试"的节奏。想在绿地功能上用 test-first 的人会读到不适用的流程。
- **不要用它硬凑测试。** 路径不清楚、需要大改 harness、或 mock 会取代真实行为时，源码要求跳过并改用最接近的检查。
- **不能替代真实表面复现。** 单元测试通过不等于 bug 消失；需要 app 级证据时用验证 skill 或 control skill。
- **不要为了迎合错误实现改测试，也不要削弱已有断言。** 除非期望行为确实变了，并且原因写清楚。
- **flaky bug 先确定化。** 尽量让测试确定，并记录它锁住的信号；如果 bug 暴露的是一类失败，先落聚焦路径，再考虑兄弟用例。
- **不自建 harness。** 新搭的测试基础设施本身就是需要被验证的东西，会把这个技能的半径撑破。

## 值得注意

- **"便宜、清晰、显而易见"没有阈值。** 判定完全由调用者做，同一个 bug 既可以被判成"值得测试"，也可以被判成"跳过"，两种结论都能自圆其说。报告三项只约束事后说明，不约束事前判定。
- **路由文字写给了错误的对象。** description 同时承载 trigger 和 skip，但 `disable-model-invocation: true` 意味着模型不能自己触发。这段判定实际靠人记得，或靠 `poteto-mode` 在读 description 时替人执行。
- **名字比内容宽。** 技能名叫 `tdd`，正文只覆盖 bug fix。用名字检索的人预期会看到 red-green-refactor，而正文没有 refactor 这一步。

## 关键洞察

1. **从未失败过的测试，信号未知。** 见证红是让绿变得可信的成本最低的方式。
2. **坏测试比没有测试更糟。** 它把错误的契约写进仓库，并教会 team 忽略红灯。
3. **测试写应然。** 镜像实现的测试在第一次重构时就失效，正好在最需要它的时候。
4. **报告证据，而不是结论。** 把"修好了"拆成失败输出、通过输出和替代方案，修复才可被复核。
