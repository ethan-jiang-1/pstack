# `technical-writing`

> 源码：[`skills/technical-writing/SKILL.md`](../../skills/technical-writing/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

先给文档选一个 Diátaxis 模式，再依次过三层句子标准：Google developer style、STE、Global English。四层之上还有三条规则，其中最重要的一条是：当规则让句子变得更难读时，改句子或干脆放过。

## 它解决什么

技术文档最常见的失败不是知道得少，而是类型错了：tutorial 里塞进 reference 表格，how-to 里开始教学，reference 里出现观点。第二常见的失败是句子没有对准读者：被动语态藏起动作的执行者，一句话塞两个念头，`this` 指代整个从句，读者需要回读才能解析。

"写得清楚"太模糊，无法逐句执行。`technical-writing` 把标准拆成层：结构层决定这份文档是什么，句法层决定每句话怎样落地，最后的判断标准只有一个，疲惫的工程师第一遍就能读懂。

## 核心机制

### 1. 四层与层序

从上到下是 Diátaxis（文档模式）、Google developer style（句子朝向读者）、STE（一次只装载一条信息）、Global English（不留第二种读法）。顺序有实质意义：模式先定，句子才有正确的目标；模式错了，每句都合格也仍然是一份错文档。

### 2. 模式由两个问题决定

内容是指导行动（doing）还是帮助理解（thinking），服务学习还是工作。四象限给出 tutorial、how-to、reference、explanation。一个文档只用一个模式；这个罗盘既可以用在整篇，也可以用在单独一句话上。混模式要拆开并链接，不能靠过渡句糊过去。

每个模式有自己的禁则。tutorial 对学习者的成功负责，每一步都要有可见结果，用 "we" 和命令式写，解释压到一句从句加一个链接。how-to 假设读者已经会了，只给动作，允许 "If you want x, do y" 的分叉，标题按任务命名（"How to calibrate the radar array"，不是 "Radar array calibration"）。reference 只描述，不指导、不说服、不发表意见，结构镜像被描述的对象，能生成就生成。explanation 是唯一允许观点的地方，围绕一个真实的 why 问题，标题前面能加上 "About..."。

### 3. Google 层：句子对着读者

用 "you" 和现在时；说清谁做什么（"the compiler checks"，不是 "is checked"）；指令写成命令（"Click Submit."）；条件放在指令之前；常见情况在前，例外在后。不要 "simply"、"easy"、"quickly"，如果真简单，读者不会在这里。标题要承载观点（"Pick the mode first"），不是只有主题（"Modes"）；一个 h1，不跳级；链接文字说明去向，不写 "click here"。

### 4. STE 层：一次一条

一句一个指令；指令超过约 20 词、其他句子超过约 25 词就拆。警告或条件放在它保护的步骤之前。保留 "the" 和 "a"，"Remove backup file" 有两种读法，"Remove the backup file" 只有一种。一个词一个含义并保持一致；一个动作固定一个词（"start" 不要一会儿换成 "initiate"）；程序写成直接命令，不写叙述也不写被动；尽量避开 "-ing"。

### 5. Global English 层：不留二义

"only" 和 "not" 贴近被修饰的词，位置不同意思不同。拆开长名词串。每个 "it"、"they"、"this" 指向唯一明显的事物，不用 "this" 或 "which" 指整个从句。不丢动词，保留 "that" 这类结构小词，系列里重复冠词，讲清 "and" 或 "or" 连接的是哪两部分。用句号不用分号，em dash 换成新句子。括号里要是完整语法单位，不写 "(s)"，不用斜杠。一个东西自始至终一个名字，同一份文档里 "the gate"、"the ratchet"、"the budget check" 指同一物，等于教了三个概念。

### 6. 三条高于四层的规则

- **删掉不干活的词。** 句子去掉某个词仍然成立，这个词就该走。
- **用短的日常词。** "use" 不是 "utilize"，"help" 不是 "facilitate"。长词必须用精确性买下它的长度。
- **规则让句子更糟时，换一种写法或放过它。** 一句遵守了所有规则却读起来像机器写的，就是失败。

第三条是元规则：它承认四层会互相冲突，冲突时读者优先。

### 7. 节奏是规则之外的一维

全是短句同样难读，而且没有观点、没有具体信息。句子长度要故意混合：短句落点，长句携带条件与后果。"一句一个念头"不等于"每句一样长"。在模式允许的地方要给出判断：explanation 可以权衡并说出结论，reference 保持干燥。具体优先于无菌，"schema changes can cause issues" 要改成 "a column rename fails the build"。

### 8. 词表就是代码库

写真实的 symbol、文件、flag、命令名，不写同义词，也不描述它。不发明术语：说 "move"、"delete"、"a budget that only decreases"，不说 "evacuate"、"ratchet"、"endgame"。一个被命名的模式第一次出现时要解释含义。发现新的隐喻词时，把它和替换词作为 `unslop` 的 rule 26 补充提案写进回复并附 diff，不要直接编辑 `unslop`。

### 9. 示范对照

末尾给了一组 before/after。before 是一句典型的套话，塞满配置说明、提醒、被动语态和悬空条件。after 只留下机制、条件和一个使用限制，还带着真实文件名 `budget.mjs` 与 `budget.json`。这一组对照把前面所有抽象规则落到了同一句话上。

## 设计意图

- **分层让"写得好"可执行。** 结构、句子、信息装载、歧义是四个不同问题，混在一起只能变成品味之争。
- **模式先于句子。** 大多数文档失败是类型错误，先修类型比逐句润色便宜。
- **元规则防教条。** 规则是诊断工具，读者理解才是目标；没有这一条，标准就会生产合规而难读的文本。
- **节奏补规则覆盖不到的地方。** 句法规则无法产生观点和具体性，只能靠单独一节要求。
- **词表来自代码库。** 术语的精确性来自引用真实符号，而不是来自更漂亮的说法。
- **隐喻词表的 owner 是 `unslop`。** 这里只引用并提案，避免两份隐喻词表各自漂移。

## 依赖关系

- **硬依赖 `unslop`。** 仓库 README 的依赖表写着 `technical-writing` 需要同时安装 `unslop`；正文要求对这份技能碰到的每份文档应用 `unslop`，并且明说 slop 目录归它管。
- **被 `poteto-mode` 路由。** 文档、RFC、readme、PR 描述、提交信息都指向 `technical-writing`。
- **`opening-a-pr`。** 每个 PR 标题、描述与 commit body 按它写，除 Diátaxis 外所有层都适用，并特别点出 STE 的词表规则（一个动作一个词、保留冠词、能用普通动词就不用 "-ing"），最后再过一遍 `unslop`。
- **`multi-phase-plan`。** 正文只用一个 Diátaxis 模式（how-to），解释与参考材料放进附录；标题陈述任务或发现；不用长破折号，不用句中冒号。
- **与 `unslop` 的分工。** `unslop` 管词表与 slop 模式，这里管文档模式与句法层。两者叠在同一段文字上，不互相替代。

## 使用边界

- **PR 描述与提交信息不用 Diátaxis。** 源码明确说这两者适用除 Diátaxis 外的所有层。它们是一分钟能读完的简报，不是文档；不要贴 swarm 日志、SHA 列表或指标表格，链接过去。
- **产品 UI 文案不适用。** 那是产品自己的 copy 指南。
- **一份文档一个模式，多模式文档要拆。** RFC 与 spec 常常同时需要 explanation、reference 和 how-to。技能给的解法是拆开并链接，或者像 `multi-phase-plan` 那样把主体收成一个模式、其余进附录。
- **英文写作标准。** Google、STE、Global English 三层都是英语规范；中文文档能直接迁移的主要是模式层和"一句一念头"这类通用约束，词表与冠词规则不能照搬。
- **不覆盖代码注释与命名。** `no-comments` 只负责移除与评审注释，不定义注释写法；命名风格也不在本技能范围。

## 值得注意

- **元规则给了违规的口子。** "规则让句子更糟就放过"在原则上是正确的，但它也让任何一条规则都可以被判断为不适用。好在 `Vary the rhythm` 一节与 before/after 示范把"机器味"这个失败模式具体化了，判断不至于完全悬空。
- **密度高，全量执行昂贵。** 四层、节奏、词表叠在一起，一份长文档逐条过一遍成本不小，实践中更容易被当作 review 清单，而不是写作时的逐步流程。
- **与 `unslop` 的禁则部分重叠。** em dash 两边都禁；分号与斜杠只在 `technical-writing` 里禁，`unslop` 没有对应规则。修改时要同步的只有 em dash 这一条。
- **两条标题规则可能打架。** reference 要求"镜像被描述对象的结构"，而标题又要求承载观点。镜像 proto 或 API 结构时，标题往往由对象决定，不一定能同时陈述观点。
- **附录解法有代价。** 把 reference 材料压进附录能让主体保持单一模式，但附录里的速查内容会变得更难被找到。

## 关键洞察

1. **先选模式，再改句子。** 类型错误的文档，逐句润色救不回来。
2. **规则服务于第一遍读懂。** 元规则把读者放在规则之上，这是整套标准能避免机器腔的原因。
3. **词表就是代码库。** 真实符号比任何同义词都精确，术语漂移会让读者以为在学新概念。
4. **节奏是四层之外的一维。** 句法全对但句句等长、没有观点，仍然读不下去。
5. **一个东西一个名字。** 同一物的三种叫法不是修辞变化，是三个需要重新学习的概念。
