# `sharpen`

> 源码：[`skills/sharpen/SKILL.md`](../../skills/sharpen/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

开工前把任务抬高一次：按顶级专家的路径看、按用户真正想要的结果看、按合适的规格松紧看，然后直接做，不交回一份改写过的 prompt。

## 它解决什么

用户给的 brief 常常同时有两种错：欠规格（没说完成标准），和过规格（把实现方式写死，甚至把猜的病因也写进去）。agent 照字面执行时，会把这些顺手写下的选择当成需求，把"用什么"当成"要什么"。

`sharpen` 在开工前插入三个问题，并要求最终保留一个外部校验。它不产出文档，产物就是被调整过的工作本身。

## 核心机制

### 1. 三个问题

正文只有一段，问句是它的骨架：

- 顶级专家会怎样做这件事：他们的 raw sources（一手来源）、真实方法，以及一个能判断结果对不对的外部校验。
- 用户真正想要的是什么。
- 任务是过规格还是欠规格。

### 2. 双向调整约束

源码的措辞是对称的：放宽不服务于目标的约束，要像增加服务于目标的约束一样自然。放宽与新增是同一个动作的两个方向，判断标准是"是否服务于目标"。同时，属于用户的选择要留空，不替他们决定。

### 3. 只加"更好"，不加"更大"

折叠进来的内容必须让工作更好，不是让范围更大。方向上接近 mode 的 **Laziness Protocol**（偏向删除和最小改动），但 `sharpen` 没有引用那条原则，也没有给出判断"更好"的标准。

### 4. 始终保留一个外部校验

"always keep one outside check that the result is right"。外部校验在开头作为专家方法的一部分出现，在结尾又作为不可省的保留项出现。两次出现说明它不是可选项：可以放宽约束、可以加约束，但不能把"怎么知道对了"一起优化掉。

### 5. 不叙述框架，不交回 prompt

不做"我先把任务 sharpen 了一下"的说明，直接做。也不交回改写后的 prompt。后者把 `sharpen` 与提示词改写工具区分开：用户收到的应该是完成的工作，不是一段更漂亮的指令。

## 设计意图

- **约束是假设，不是事实。** 用户写下的实现选择，可能只是他顺手想到的第一个方案。
- **对称调整比单向加约束更接近真实判断。** 只会加约束会把任务越做越大，只会放宽会丢掉真实要求。
- **留白是决定权。** 产品取舍属于用户，agent 把它填上就是替人做了决定。
- **不输出元信息。** 把"我这样理解你的任务"再说一遍，既占篇幅又容易被当成已完成。
- **用一段话而不是清单。** 它约束的是判断方向，不是步骤顺序，所以不需要编号。

## 依赖关系

- **上游**：人输入 `/sharpen <task>`；`poteto-help` 的 **Pick a skill** 表把用途写成"Aim a task higher before starting"；[`recipes.md`](../../skills/poteto-help/references/recipes.md) 的 **Understand** 一节给了 `/sharpen <your task>` 示例。
- **下游**：不指定下一步，通常接 `poteto-mode` 或某个单点 skill。
- **共享**：与 `prompting.md` 的 **Leave out** 一节目标相近，都反对用实现细节冒充需求；但那边是写给用户的 prompt 建议，这边是 agent 的开工前自查。
- **对照**：`in-your-own-words` 检查理解是否正确，`sharpen` 改变接下来怎么做；`poteto-help` 回答该用哪个 skill，不碰任务内容。

## 使用边界

- **不是澄清器。** 它把用户的选择留空，但不向用户提问。真正的产品取舍仍要靠人在别处解决。
- **不产出可审的中间物。** 没有 plan、没有约束清单，用户只能从结果反推它做了什么。
- **对合规性约束要小心。** 源码允许放宽"不服务于目标"的约束，但 agent 未必分得清某条约束是用户的随手选择，还是来自合规或安全要求。
- **不替代理解。** 它改的是任务框定，不是代码理解；需要机制或动机时仍要 `how` 和 `why`。
- **没有分档。** 任务大小和领域都不改变它的动作，所以它不会因为任务小就自动跳过这一步。

## 值得注意

- **压缩到一段的代价。** 三个问题、双向调整、一个保留项、两个禁令都在一段正文里，没有编号也没有完成条件。执行与否只能从结果反推，这是它与 `how`、`why` 这类带固定小节 skill 的最大差别。
- **"留空"与"直接做"之间没有出口。** 源码要求把用户的选择留空并继续做，不停下来问。
- **外部校验没有定义。** 源码只说"an outside check that the result is right"，没给具体形式，也没说校验失败后是重做还是上报。
- **放宽是不可见的。** 正文要求不叙述框架，所以用户看不到哪些约束被放宽；放宽错了，只有结果会暴露。

## 关键洞察

1. **brief 是假设的集合，不是需求的集合。** 原样执行，等于把用户顺手写下的猜测放大成需求。
2. **放宽和收紧是同一个判断的两个方向。** 只做一边，就会在过规格和欠规格之间来回摆。
3. **不交回 prompt，是把提升落在工作上。** 改文字比改做法便宜，也更容易变成表演。
4. **一个外部校验不能省。** 可以改约束，不可以改判断对错的方式。
5. **最便宜的规格修正发生在开工前。** 开工后再补验收，代价是返工。
