# `blast-radius`

> 源码：[`skills/blast-radius/SKILL.md`](../../skills/blast-radius/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

在合并前回答"这个改动会在别处弄坏什么"，并且拒绝交一份听起来对的报告：找出整个判断所依赖的一两条事实，用真代码跑出来证明，证明不了就写 unproven。

## 它解决什么

一个看起来很小的 diff，可能因为被调库的语义、执行时机（microtask、unmount、teardown）、API 返回的 JSON、数据库列、wire format、feature flag，或者三跳之后的调用者而坏掉。grep 调用者几秒就能做完，agent 也擅长把这些写成一篇结构完整、读起来很有道理的风险分析。

问题在于：这份分析无论真假都读起来很有道理。`blast-radius` 的立场是不要相信自己的 writeup，把结论压到能失败的东西上——一段真的会跑的代码。

## 核心机制

### 1. 读改动，包括 diff 没写出来的部分

看 diff、新增与修改与删除的符号、现在行为有什么不同。上下文用 `why` 的 Step 2 去拉相关的 PR 和 commit。

### 2. 找那条"安全所依赖的事实"

多数看起来危险的改动之所以安全，是因为一条事实：例如"这次调用只丢弃已经失效的缓存项，别的什么都不做"。找到它，它成立就一次性清掉大部分风险情况。时间花在这里，不花在一长串"可能"上。整个 skill 的预算分配由这一条决定。

### 3. 看 grep 停下的地方

读你调用的那个库的源码，确认 pin 的版本和有没有本地 patch。搞清楚什么时候运行：microtask 的顺序、unmount 与 teardown、Solid 与 React 的差异。跟符号搜索看不到的东西：API 返回的 JSON、数据库列、wire format、另一种语言读同一批字节、feature flag、三跳之后的代码。

### 4. 诚实标注每条风险

给每条风险真实的发生概率和真实的代价。留下的叫风险，查过并排除的单独列成 cleared。规则与 `why` 一致：引用真实 `file:line`，搜不到调用者也是答案，绝不发明一个调用者或一个 API。

### 5. 证明那条事实

写一个脚本或测试，调用真实代码，运行，然后把实际发生的东西贴出来。这是唯一一步能当场证明你错了的步骤。

### 6. 大改动交给 `arena`

范围宽或影响深的改动，用多个模型回答同一个问题再合并答案。不同模型会抓到不同的真 bug。

### 置信阶梯

源码给了一个五级阶梯，用来给"安全所依赖的每条事实"定位：

1. **你说如此。** 单独拿出来没有价值。
2. **你指到了行。** 真实的 `file:line`，或者库自己的源码。
3. **你证明坏情况不会发生。** 把失败路径一步步走完，确认走不到。
4. **你跑过。** 一个脚本或测试调用真实代码，如果你错了它会响亮地失败。
5. **你在运行中的应用里复现过。**

每条事实尽量往下走，并明确说停在哪一级。第 4 级通常就是一个小脚本：import 应用实际发布的那同一个库，调你担心的那个函数。

### 交回什么

- **What it does**：改了什么，包括不明显的部分。
- **The one fact it's safe because of**：陈述这条事实，说明它到了阶梯的哪一级，给出证明；证明不了就写 unproven。
- **Risks**：每条写清怎么坏、`file:line`、可能性与严重度、怎么检查；重要的那条要贴出证明。
- **Cleared**：查过什么，为什么没问题。
- **Before you merge**：能抓住真 bug 的最便宜的测试或复现，包括你写的那个脚本。

输出过 `unslop`，引用真实代码，公开前清掉私有内容。

## 设计意图

- **可证伪优先于可读。** 五级里只有"跑过"和"复现"能失败，前三级都是叙述。skill 把交付物从报告改成证明，是在修正 agent 最擅长的失败模式。
- **单点承重。** 与其罗列十个 maybes，不如找一条承载大部分判断的事实，把预算压在它上面。
- **拒绝交付 writeup 是对自身说服力的防御。** 模型生成连贯解释的能力和解释的真实性不相关，所以不能让连贯性成为交付标准。
- **用 `arena` 对冲单模型盲区。** 不同模型对同一段代码的失败模式敏感度不同，宽改动值得多一双眼睛。

## 依赖关系

- **上游**：`how` 给出代码做什么，`why` 给出为什么长这样，并提供 Step 2 的 PR 与 commit 拉取方式；`git`、`gh`、项目自己的测试框架提供执行手段。
- **下游**：合并前的检查；`poteto-mode` 的 `orchestrate` playbook 在验证昂贵、依赖判断或 blast radius 高时派独立 verifier；`docs/guide/06-verify-and-ship.md` 推荐对不放心的小 diff 用它。
- **共享**：`arena`、`unslop`、`why` 的证据纪律。
- **对照**：`interrogate` 评审 diff 本身；`blast-radius` 看 diff 之外的破坏，并证明那条让改动安全的事实。

## 使用边界

- **它不替代测试套件。** 产出是"合并前最便宜的检查"，不是长期覆盖。
- **适合"小 diff 但不确定"。** 大改动可以借 `arena`，但仍要落到可证明的事实上。
- **不是所有环境都能跑到第 4 级。** 基础设施配置、跨语言字节、feature flag 组合，跑真代码可能很贵或做不到。此时诚实的输出是 unproven 加最便宜的检查建议，而不是把弱证据写强。
- **不判断改动值不值得做。** 那是评审和产品判断。
- **没有 PR 或 commit 时**（本地未提交改动），Step 2 的上下文拉取退化为直接读 diff。

## 值得注意

- **"一条事实"假设风险集中在单点。** 如果改动同时动了 wire format 和重试语义，两个失败模式互相独立，一条事实证明不了整体安全。源码在开头允许"one or two facts"，但没有说多条事实时证明预算怎么分。
- **置信阶梯是自评的。** 没有外部检查确认"确实跑过"；源码用"把发生的东西贴出来"制造可核查性，但读者仍要自己判断那段输出是否真的覆盖了担心的情况。
- **证明脚本是一次性的。** 源码没有要求它进仓库或进 CI，所以证明只对这一次合并有效，同类改动下次要重做。这是有意的低成本，也是它无法积累的原因。
- **五级阶梯的措辞是作者视角**（"你说如此""你跑过"），容易被读成对 agent 的评分标准，而不是对事实的证据分级；实际约束的是每条风险陈述的证据强度。

## 关键洞察

1. **报告的说服力和真实性无关。** 所以要用能失败的东西做证据。
2. **找承重事实比穷举风险更省预算，也更容易被推翻。** 一条事实错了，整个判断就塌，这正是它的价值。
3. **grep 的边界就是风险的边界。** 调用者可见，语义和执行时机不可见。
4. **Risks 与 Cleared 分开写。** 防止把排除过的项混进风险清单充数。
5. **明说停在阶梯哪一级。** "unproven" 比含糊的肯定更有用。
