# `in-your-own-words`

> 源码：[`skills/in-your-own-words/SKILL.md`](../../skills/in-your-own-words/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

让 agent 在动手之前，用它自己的话复述它认为你要达成的目标，以及你要解决的问题。

## 它解决什么

长、乱、带猜测的需求容易在开头就被误读。误读在代码出现之前最便宜被发现：一旦开工，错误的理解会被后续步骤层层固化成实现。

同样的动作在 [`prompting.md`](../../skills/poteto-help/references/prompting.md) 的 **Load the context first** 一节里也出现过：对嘈杂的报告，先让 agent 用平实英文复述底层问题，再做别的。误解会先于任何代码暴露。

## 核心机制

### 1. 只做一件事

复述两个对象：goals（你要达成什么）与 problem（你在解决什么）。两者不等价：目标可以是"重试后别发两条通知"，问题可能是"重试路径把同一次事件写了两遍"。把二者分开，才能看出 agent 是不是把症状当成了目标。

### 2. "用自己的话"是要求，不是修辞

不是引用原文，不是摘要，不是把需求改写成条目。用自己的话意味着必须重新组织因果：谁做了什么、导致什么、哪里不对。只有真的建立了模型，才组织得出来。

### 3. 没有规定的输出形状

源码只有一句正文：没有小节、没有长度、没有"先复述再确认"的流程，因此输出形状随上下文变化。这不同于 `how`、`why` 这类带固定回报格式的 skill；那边模板就是接口，这边接口就是"复述"这个动作本身。

description 与正文也几乎逐字相同，没有独立的触发条件文本。看到名字就等于看到做法。

### 4. 单点、由人触发

`disable-model-invocation: true`，模型不会自己调用它；mode 的 **Non-negotiables** 里也没有它的条目。它由人直接输入，或从 `poteto-help` 的表格里被发现。

## 设计意图

- **先对齐再执行。** 误读越早发现越便宜，这条 skill 把发现点放在第一次输出之前。
- **用自己的话强制建模。** 抄原文可以绕过理解，复述不能。
- **目标与问题分开。** 症状和目标混淆是最常见的误读，分开复述能让它显形。
- **不绑定后续动作。** 它只要求复述，不规定复述之后做什么，因此可以接任何流程。

## 依赖关系

- **上游**：人输入 `/in-your-own-words <ask>`；`poteto-help` 的 **Pick a skill** 表把它描述为"Check that the agent understood their goal and the problem before it starts"；[`recipes.md`](../../skills/poteto-help/references/recipes.md) 的 **Understand** 一节给了带长 ask 的示例。
- **下游**：不指定下一步，通常接 mode 的 playbook 或某个单点 skill。
- **共享**：与 `prompting.md` 的 **Load the context first** 第一条同义；与 `sharpen` 占据同一个"开工前"位置，但一个校准理解，一个校准规格。
- **对照**：`bro` 复述 agent 自己的上一段回复；`ketchup` 汇总一段对话的变化；`recall` 跨会话重建上下文。

## 使用边界

- **不解决歧义。** 它只暴露理解，不提问、不要求确认。复述错了，用户要自己看出来并纠正。
- **不覆盖约束与验收。** 它只复述目标与问题，而 `prompting.md` 要求 prompt 里写清完成检查和真实约束；这部分它不管。
- **源码没有"先别做"的边界。** 与 `poteto-help` 明确写"don't start the work"不同，这里只要求复述；复述完是否继续执行取决于上下文。
- **对已经清楚的任务是纯开销。** 多一次往返，换一个用户已经知道的理解。
- **复述质量取决于上下文。** 没有代码、日志、复现步骤时，"自己的话"可能只是把用户的猜测换个说法。
- **发现成本落在人身上。** 它不会自己触发，也不在 mode 的触发表里；只在仓库 README、`poteto-help` 的表格和 recipes 的示例里被列出。

## 值得注意

- **只做一件事的 skill，行为几乎完全由调用时机决定。** 同一句话在长对话开头和结尾，复述的粒度会差很多；源码没有给它任何稳定形状。
- **与 `bro` 容易混。** 两者都叫"复述"，对象不同（用户的目标 vs agent 的回复），而两页正文都没有互相指路。
- **没有确认环节。** 复述完就结束；用户不纠正，流程就继续往下走，误解不会被拦住。
- **与 `sharpen` 位置重叠。** 都在开工前，一个改规格、一个验理解；同时用会多一次往返，源码没有说明顺序。

## 关键洞察

1. **最便宜的对齐发生在写代码之前。** 一旦进入实现，纠错的单位从"一句话"变成"一个 diff"。
2. **"用自己的话"是防抄写的机制。** 抄原文可以绕过理解，复述不能。
3. **只复述目标与问题，不复述方案。** 方案会让猜测提前固化成计划。
4. **缺形状的 skill 把责任放回调用时机。** 什么时候用，比怎么用更重要。
