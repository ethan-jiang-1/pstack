# `correct`

> 源码：[`skills/correct/SKILL.md`](../../skills/correct/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [环境即产品](../patterns/environment-as-product.md)

## 一句话

把 operator 反复纠正的同一类错误，变成仓库里最强的可行约束：先让架构使错误写不出来，再让类型使错误编译不过、lint 让 CI 拦住，再让测试抓住回归，文档永远最后；每条新检查都要先在一条真实历史错误上失败。

## 它解决什么

源码把 contributor 建模成 agent，并给出三条行为假设：它只看自己打开的文件，抄最近的例子，走能编译的最短路。在这个模型下，"单文件里看起来对"的改动完全可能对整仓库是错的，因为正确做法在另一个文件里，或者只存在于一个过时的例子里。

人在 chat 里纠正只帮一次，下次换个 agent 又犯。所以 `correct` 的产物不是一条说明，而是仓库结构。它先定什么算一类错误：同一类错误出现两次才计数，证据来自 recent commits、reverts、review comments、agent instruction files，以及解释 workaround 的注释。第二次出现就是把纠正升级成约束的时刻。

## 核心机制

### 1. 按"能工作的最高层"修

源码给的是一个约束阶梯，顺序本身就是内容：

1. **用架构消除它。** 每块状态一个 owner，每个任务一条受支持路径；隐藏内部让错误 import 直接失败；手同步的列表换成一个真相源；删掉旧方式和 agent 会抄的死代码。
2. **用类型让坏状态写不出来。** 如果坏代码仍能编译，加一条 lint 或 CI 检查，并让错误信息点名该用哪个文件、类型或函数。模式已经很普遍时，只在一次改动新增了更多时才失败（ratchet）。
3. **用测试锁行为。** 修或删那些"行为坏了仍然通过"或"只改内部就失败"的测试。
4. **文档与 agent 规则放最后，只用于判断类问题。** 源码给的理由很直接：agent 跳过它们时没有任何东西失败。

`description` 把 lint 列成独立一步，正文把它并进第 2 条。机制上是同一层：类型表达不了时才用 lint 追，两者都在"错误无法通过检查"这一档。

### 2. 修并证明

先修最频繁的类，一个 class 一个 commit。每条新检查都要证明它在一条真实历史错误上会失败，否则它可能是一条永远绿的装饰。同一条命令本地和 CI 都要跑，这保证"通过"在两边含义相同。例外写在违规那一行上，带理由、到期日、人的批准，而不是散在文档里。

### 3. 维护规则表

最后在 agent instruction file 里维护一张表，把每条规则与强制它的机制配对。之后每次被纠正：修掉错误，并把规则加进表。如果规则已经在表里而没有任何东西强制它，这就是一次 repeat，说明它停在最弱的层级，必须在同一次改动里升层修。错误已经不可能发生时，把规则删掉，表随约束变化。

### 4. 回复形状

每个类给出证据、选了哪一层、以及为什么更高层不成立。最后一项是关键：它迫使执行者证明阶梯的上层真的不可行，而不是顺手写一条 lint 了事。

## 设计意图

- **按 agent 怎样读仓库来设计仓库，而不是按人怎样被说服。** 一篇"请使用 repository 层"的文档不会改变最短路径；让直接 import 编译失败会。
- **阶梯等于失败时机的阶梯。** 架构让错误写不出来，类型让错误编译不过，lint 让 CI 挂，测试让回归被捕获，文档什么都不拦。强弱不是偏好，是谁在什么时候发现。
- **一个 class 一个 commit。** 证据可归属，出问题可定点回退，也防止把架构改动和规则改动混成无法评审的一团。
- **ratchet 而不是全量失败。** 当一个错误模式已经遍地都是，全量失败会逼出两种坏结果：一次大规模重构，或者检查被直接关掉。只拦增量让新代码先干净。
- **规则表暴露 enforcement gap。** 一张"规则 → 强制者"的表本身不强制任何东西，但一张空着强制者那一列的表会让缺口显形。

- **上游**：[`architect`](../../skills/architect/SKILL.md) 用于"修复是画一条新边界"的情况，例如给状态指定唯一 owner、把内部藏起来。

## 使用边界

- **没有重复证据就不该动手。** 一类错误只出现一次时，正确产物是一条待观察的记录，不是一次架构改动。
- **需要一条可被本地和 CI 共同执行的命令。** 没有 CI 的仓库只能执行阶梯的前半部分，检查失去了强制力。
- **例外机制依赖组织流程。** 到期日与人的批准是源码的硬要求；没有这个流程时，例外会退化成口头豁免，而它恰恰是最容易腐烂的一层。
- **架构级修复可能超出一次 run 的预算。** 源码只规定先修最频繁的类，没有规定其余各类怎么办，这是执行时需要自己补的决定。
- **它不是重构 skill。** 改动范围由错误类决定；"顺便整理一下这个模块"超出了它的问题定义。

## 值得注意

- **阶梯没有判据。** `highest level that works` 仍是一次判断，源码没有给"架构不可行"的可检查条件，所以"为什么更高层不行"只能靠执行者的论证质量。
- **证明失败需要一条可重放的历史错误。** 源码把"在真实历史错误上失败"当作硬要求，但没说什么类型的错误没有可重放样本。没有样本的类只能靠执行者判断，要么落成结构性收紧，要么退回文档层，这一步没有检查。
- **规则表是它自己排序里最弱的一层。** 表在文档里，跳过表没有任何东西失败。源码用 repeat 来探测这个漏洞，但探测依赖人继续纠正：如果人不再指出，缺口就一直不可见。
- **一个 class 一个 commit 会拉长历史。** 类很多时没有合并策略，只有"最频繁的先修"这一个优先级。

## 关键洞察

1. **约束的强度就是违反时谁会发现。** 把纠正放在最晚发现的那一层，等于接受它继续发生。
2. **让错误 import 失败，胜过写一篇"不要这样 import"。** 结构比劝告更接近不可违反。
3. **规则表的价值不在记录规则，在暴露没有强制者的规则。**
4. **先证明检查会红。** 一条从未失败过的检查，和没有检查的区别只是维护成本。
