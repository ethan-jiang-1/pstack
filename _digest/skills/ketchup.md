# `ketchup`

> 源码：[`skills/ketchup/SKILL.md`](../../skills/ketchup/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

把"你离开这段时间里这个 chat 发生了什么"压成一份正文远低于 150 词的平实更新：开头一句说有几件事等人拍板，图先行，然后每个行动项两行上下文，足够人当场做决定。

## 它解决什么

人离开一会儿再回来，面对的是几十条工具调用、subagent 回报、PR 与 CI 状态变化。默认的汇报会写成"CI 绿了、commit `abc1234`、12 个测试通过"——那是给机器核对用的日志，不是给人读的消息。`ketchup` 的假设很具体：用户记得自己上一条消息，之后一概不记得。所以它只讲那之后发生的变化，并把每条变化说到"能据此行动"的粒度。

它同时处理一个反方向的诱惑：为了显得有产出而编造行动项。源码反复要求"没有等人的事就说没有"，"绝不为了填满回复编一个决定"。

## 核心机制

### 1. 起点是用户的上一条人类消息

摘要窗口从用户写下 `/ketchup` 之前的那条消息开始。通知和 subagent 结果不算用户消息。这条例外很关键：subagent 完成通知在 transcript 里长得像一条新输入，但它不是用户的记忆锚点。

### 2. 采集保持只读

这一轮不改代码、不启 app 或 job、不发任何东西；视觉素材只能用手上已有的事实。要核对每个将展示的数字，发现错了要说明更正。本 chat 碰过的 PR、CI run、agent 都要查当前状态，而不是复述几分钟前的状态。

### 3. 行动项的定义收得很窄

只有用户能做的决定或步骤才算：产品选择、审批、不可逆动作、agent 没有的权限。之前提出、至今仍在等用户的也算。agent 自己还能做的工作不是行动项。没被要求、工作也不需要的一步也不是，除非它不可逆且卡在用户这里——那种情况只给一行，不配图，也不写"不回答会怎样"。

### 4. 回复形状

开头一句说明有几件事需要用户，或者没有。什么都没发生且没人在等，说完就停。然后图先行：内嵌工作产出的截图和视频，再放解释变化的图。接着一条短 bullet 对应一个用户要求过的事项，写清结果以及 done、running、failed 还是 not checked，每行单独读也要成立，顺带点名路上发现并修掉的 bug。再给最多三条改变认知或行动的短句，再一行 agent 自己还能做的剩余工作。最后才是行动项列表：纯 bullet，每项两行——决定、你的建议及理由，以及用户不回答会怎样；不可逆的未要求步骤一行。

### 5. 视觉的边界

视觉指截图、视频、Mermaid、`/visualize`（Cursor）或 harness 的图表工具、生成图。Markdown 表格再像也不是视觉。每张图最多六个框，每框最多八个词；标签用日常话说，不写 `Tests: pass` 这种字段式标签。可见变化没有截图就标 "No screenshot yet" 并说明屏幕上变了什么。

### 6. 预算与优先级

正文（不含图）远低于 150 词。同一事实不出现两次，文字和图之间也不重复。没有改变用户处境的工作直接不写。词数不够时先砍"发生了什么"，再砍行动项——行动项是这份回复最不可压缩的部分。

## 设计意图

- **把"给人读"从"给机器读"里拆出来。** hash、文件路径、测试计数是证据，不是消息。它们只在用户需要其中一个来行动时才出现。
- **先图后文是带宽排序。** 空间关系、前后对比、依赖链在文字里最贵，在图里最便宜。
- **行动项两行结构是在替用户省一轮追问。** 决定、建议、理由、不回答的后果，四件事齐了，用户扫一眼就能拍板。
- **开头一句是路由。** 告诉用户有几件事在等，让他决定现在读还是稍后读，而不是先读完才知道要不要读。
- **保守优先。** "Never make up a call"、"Write unknown"，都是宁可少说也不虚构。

## 依赖关系

- **上游**：`poteto-mode` 的 `autopilot-full` 与 `autopilot-stack` playbook 把 `ketchup` 当作 tick 结束时和收尾时的回报形状（"catch the operator up per the **ketchup** skill"）。
- **共享**：`bro` 提供声音——plain words、短句、无术语——但明确不承担任务；`/visualize` 是 Cursor 的命令，其他 harness 用自带图表工具。
- **对照**：`recall` 重建跨 chat 的工作上下文，`ketchup` 只覆盖本 chat 自用户上一条消息之后；恢复某个具体 session 属于 `session-pickup` playbook。

## 使用边界

- **只管本 chat。** 跨会话、跨天的工作状态用 `recall`。
- **只读。** 它不修 CI、不重跑失败任务，只报告；需要动手时那是另一个 turn 的事。
- **不替用户做决定。** 源码要求"Ask the call the user owns"，建议可以给，拍板必须留给用户。
- **不产出 PR 体或文档。** 那些是 `technical-writing` 的领域。
- **没有内容时必须说没有。** 空回复比编出来的行动项好。

## 值得注意

- **`/visualize` 是 Cursor 专属。** 源码在同一段里既把它写成可得的图表工具，又用括号标注了 harness 差异。换到别的 harness，视觉能力退到 Mermaid 或通用图表工具，而"图先行"的结构要求不变。
- **150 词预算与多行动项会互相挤压。** 源码给的优先级是先砍变化叙述，这意味着行动项一多，"发生了什么"会被压到接近零。这是有意的取舍，但在长任务收尾时读者可能失去上下文。
- **六个框的上限对依赖链很硬。** 一个 PR stack 超过六层就画不下；源码没有给超限时的降级方式，只能改用文字或拆图。
- **行动项两行、选择项另算收益与代价**，两套格式在同一份回复里并存，选择放在行动项列表之后；源码没有说明的是同一条目是否在两处重复。

## 关键洞察

1. **摘要的稀缺资源是读者的注意力，不是 token。** 少写是功能，不是省事。
2. **先图后文是带宽排序。** 同一份事实，选错载体就要读者自己重建空间关系。
3. **行动项要自带决策上下文。** 没有建议和后果的行动项只是把问题原样扔回去。
4. **只读加上核对数字**，让"catch up"不会变成第二次错误。
5. **"假设用户只记得上一条消息"是一个可复用的摘要范围定义。** 它把"最近发生了什么"这种模糊要求变成了明确边界。
