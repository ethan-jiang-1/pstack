# `no-comments`

> 源码：[`skills/no-comments/SKILL.md`](../../skills/no-comments/SKILL.md)
> 调用：**U**（user-invoked，只有人能触发）
> 索引：[技能索引](./README.md) · [系统总览](../system/README.md)

## 一句话

把注释交给一个没写过这些注释的只读评审者，按一张很短的豁免清单决定去留。留下的"约束型"注释要么被编码成类型、测试或 lint，要么删除并把约束记为未执行风险。

## 它解决什么

注释有两种失败方式，处理方式相反。第一种是噪音：叙述代码已经说清楚的事、横幅、被注释掉的尸体、为绕路写法辩护的说教。第二种是伪装成文档的约束："do not remove"、"这里必须这样"、"改之前先问 X"。它可能装着真实的外部知识，但没有任何机制保证它被遵守，也没有机制保证它仍然为真。

`no-comments` 同时处理这两类，做法不同。噪音被删除，理由由一张白名单判定。约束被当作待编码的声明：能找到便宜的类型、运行时检查、测试或 CI lint，就先编码再删注释；找不到就删掉，并把它作为未执行的约束报告出来。前一种让知识进入机制，后一种让风险变得可见。

作者为自己的注释辩护的程度，和自己为代码辩护差不多，所以评审者必须是没参与写作的一方。这就是 Comment Sicko 存在的理由。

## 核心机制

### 1. 角色分离

三个角色不重叠。Comment Sicko 只读、只报，报告只有四项：碰过的文件、删除数、逐条一行的 `MUST KILL` 标记、跳过项。它的原话是 kill 到此为止，不碰代码。调用方负责裁决，第 4 步才实现修复。评审因此不会被"顺手改一下"污染。

### 2. 豁免清单是白名单

只有几类注释能活：法律或许可头；由外部依赖、平台、厂商或协议强制、而我们无法重塑的非显然行为；`// prettier-ignore`；规则本身有错、过于迂腐或只管风格的 lint 抑制；定义公开 API 契约的文档注释；解释代码无法表达的约束的 issue 或 RFC 链接。源码说得直接：这张清单是唯一的缰绳，不确定时注释就死。

### 3. 自家代码的意外是肉

同一份 prompt 把"外部强制"和"我们自己代码反直觉"分开。后者不享受豁免，注释被删，并把精确符号标成 `MUST KILL`，指向 rename、extract、类型化或重构，让行为不靠散文也显然。这条把注释问题转成了代码可读性问题。

### 4. 抑制指令单独审

`eslint-disable`、`@ts-ignore`、`@ts-expect-error` 不按普通注释处理。要先查规则：如果它抓的是真 bug，或在保护正确性与安全性，就删掉抑制，并把有罪的符号标成 `MUST KILL`。audit 还要求覆盖被跳过的 scoped lint 与 TypeScript 抑制。

### 5. 裁决有明确的默认值

调用方要拒掉几类报告：改应用代码、越出 scope、删了受豁免保护的注释、`MUST KILL` 理由说错、把保留的有意代码当成有罪。对那些薄的 `IMPORTANT` 或 `do not remove`，接受之前要对该符号跑 `/how` 或 `/why`。歧义的 kill 不恢复；被驳倒或仍然歧义的 keep 删除。一份被拒的报告可以带着失败原因重跑一次；第二次被拒就报告为 open，并让整次 `/no-comments` 失败。

### 6. 修复止于根因，不止于症状

trivial 的 flag 直接做：删死路径、去掉参数、改用真实 API。需要形状时只跑一次 `/architect`，停在 sketch，由第 4 步实现。然后做范围内最小的根因修复，移除所有被点名的绕路写法。根因在范围外时，落最小的范围内修复，其余报告为 open。技能点名两个 principle 只指导意图，不授权扩大 fence，也明确禁止贴症状级 guard。

### 7. 约束的出口是编码

第 5 步处理约束型注释。对 "do not remove"、"do not change wording"、"talk to X before changing" 这类，技能要求提出范围内最便宜的类型、运行时、测试或 CI lint 方案，等待交互批准。无人值守与 eval 场景需要调用方预先批准。批准则先编码再删注释；不批准则删注释、把约束报告为 open、并勾出范围外的工作。对于已经证明是关于我们无法改变之物的 keep，则原样保留。

### 8. 报告项固定

删除数、恢复的注释、重跑次数、architect sketch、修复、编码提议、实际编码、未执行的约束、其他 open 工作。报告本身就是交付物。

## 设计意图

- **陌生视角。** 作者会为自己的注释和为自己的代码一样辩护，只有没写过的人才会问"这句到底买到了什么"。
- **两类注释，两条路径。** 噪音直接删；约束先尝试机制化，机制化失败才作为风险暴露。删除不是目的，把知识放到正确的位置才是。
- **默认怀疑。** 白名单短、歧义归删除，让系统在信息不足时选择更小的产物，恢复成本由版本控制兜底。
- **MUST KILL 保留知识。** 如果只删注释，行为仍然反直觉；标出精确符号，删除才附带下一步。
- **一次重跑上限。** 防止 agent 与评审者无限拉锯，也防止 agent 用重跑掩盖自己没读懂报告。
- **原则不扩权。** 显式写明两个 principle 只指导意图，避免 `/no-comments` 长成一次重构。

## 使用边界

- **它不改应用代码。** 评审者报告，调用方裁决，第 4 步才实现；不要让评审顺手改。
- **它不扩 scope。** 超出调用方给定文件或 diff 的问题只报告 open，不修。
- **它不设计架构。** 需要新形状时 `/architect` 只给 sketch，实现仍归本技能的修复步骤。
- **不处理文档、PR 描述、提交信息。** 那些属于 `technical-writing` 与 `unslop`。
- **外部约束没有可用编码时，正确结果是删除并报告。** 源码把"保留但未执行"视为失败状态，而不是可接受的折中。
- **无人值守时不能临时征求编码批准。** 没有调用方预先批准，就只能走删除加报告 open 的分支。

## 值得注意

- **裁决是整个流程最重的判断。** 第 2 步要在几类拒绝理由之间分辨，还要为薄的 `IMPORTANT` 额外跑 `/how` 或 `/why`。省掉这一步，就会把真实的外部约束当 slop 删掉；不省，成本就落在调用方身上。
- **一次重跑上限放大了单点失败。** 一份报告被拒两次会让整次 `/no-comments` 失败，于是一个理由写得不好的 flag 可能拖垮整轮，即使其余删除都是对的。
- **默认删除依赖版本控制可恢复。** 代码注释可以从 git 历史找回；但注释里记录的外部系统知识，比如某个厂商接口为何必须这样调，删掉之后往往只能从 PR 讨论里挖。
- **`MUST KILL` 只给符号，不给预算。** 它把"代码该改"标出来，但没有规定谁在什么时候改，所以这个列表可能长期悬空。

## 关键洞察

1. **注释需要外部评审。** 作者对自己注释的辩护和对自己代码的辩护一样不可靠。
2. **白名单短，默认怀疑，歧义归删除。** 三条合起来让"保留"成为需要举证的一方。
3. **自家代码的意外说明代码没写好。** 正确修法是让行为自明，不是写更长的注释。
4. **约束的归宿是机制。** 类型、测试、lint 能表达的约束不该靠散文维持；表达不了的，就该被看见。
5. **原则是意图，不是扩权。** 引用 principle 不能让清理任务变成重构任务。
