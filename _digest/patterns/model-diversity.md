# Model Diversity 模式

## 是什么

pstack 把"换一个模型"当成一种结构性输入，而不是备用方案：`arena` 用不同模型生成候选，`interrogate` 用不同模型做对抗评审，`swarm` 用不同模型分组比赛，`reflect` 用不同视角复查同一段会话，`shipping` 要求验证者是没有写这份代码的 agent（不同模型是更强的独立性，不是硬条件）。

![模型面板、候选、评审与验证的关系](../figures/model-panel.svg)

## 三种用法

### 1. 生成候选

`arena` 给所有候选同一个 prompt，每个候选跑在自己的输出位置。它不要求候选"扮演不同角色"；差异来自模型本身。

裁判从 `arena cross-judge pool` 里优先选一个与父模型不同家族的模型，按事先写好的 rubric 逐项打分。父 agent 自己也会读完全部候选，再与裁判结论对照：一致就确认，不一致就读双方理由。

### 2. 对抗评审

`interrogate` 按 `interrogate reviewers` 的列表，一个模型一个 reviewer，各拿同一份 diff 和 rubric。它明确说"对抗信号来自模型多样性，不来自分配人设"。

综合时，两个以上模型独立提出的问题信号最高；单独一个模型的发现要读，但权重降低；互相矛盾的发现要记录。

### 3. 独立验证

`shipping` 要求每个 PR 的 verdict 来自**没有写这份代码**的 agent。`show-me-your-work` 要求交付前由一个不同模型家族的 subagent 复查 decision trail。

独立性有两个维度：不同的 agent，不同的模型。`shipping` 的硬条件只是前者；`show-me-your-work` 的复查明确要求后者。只换 agent 不换模型，仍然可能共享同一个盲点。

## 为什么有效

- **错误相关性低。** 同一模型重复跑，错误往往同源；不同模型的训练数据、对齐方式和失败模式不同。
- **一致是强信号。** 多个模型独立得出同一结论，比一个模型说得很确定更可信。
- **分歧也是信息。** 分歧暴露 rubric 的歧义、上下文的缺失，或某个模型真的看到了别人没看到的东西。

## 代价

- **成本成倍。** 两个候选加一个裁判，至少三次完整生成；`swarm` 的 N 个 worker 是 N 份成本。
- **模型目录会漂移。** 默认 slug 是快照，换 harness 或模型下架时要降级。
- **面板可能退化。** 如果所有角色都配成同一个模型，多样性收益消失，但流程看起来仍在运行。
- **综合者仍是单点。** 最终判断由父 agent 或 lead reviewer 做，模型多样性不能替代判断质量。

## 怎么迁移

1. 先问"这里需要的是更多候选，还是独立判断？"候选用 arena，判断用 interrogate，覆盖用 swarm。
2. 把模型选择集中到一个设置文件，按角色而不是按 skill 配置。
3. 裁判或验证者尽量与生产者不同家族。
4. 事先写 rubric，不要让裁判凭整体感觉选。
5. 记录分歧，不要为了统一而抹平。

## 关键洞察

1. **多样性是手段，独立性才是目的。** 不同模型只是获得独立性的一种便宜方式。
2. **一致与分歧都要解释。** 一致确认结论，分歧暴露问题；只看多数票会浪费后者。
3. **面板要防退化。** 同一个模型填满所有角色，流程还在，收益没了。
